Business proposition
1. The Market Gap & The Pain Point
The Status Quo
The Kenyan government enacted severe structural bans on gambling promotions. Betting operators legally cannot use public figures, influencers, or lifestyle marketing. They cannot use aggressive calls-to-action ("Bet Now!"), and they cannot show testimonials of people winning. 
The Hidden Backdoor ("Dark Social")
Despite this, Kenya has the highest betting engagement rate in Africa (~83%). Because people can no longer rely on mainstream ads, sports discussions and "tips" have moved entirely underground into private peer-to-peer networks—specifically thousands of hyper-active WhatsApp Groups, Telegram Channels, and Facebook Groups. 
The Core Problem
Betting companies are sitting on massive cash reserves but have no scalable, compliant digital customer acquisition channel. They have raw affiliate links, but they can't manage or track thousands of everyday micro-tipsters organically sharing "multi-bets" inside private chats.
2. The Engine: "The Social Slip Protocol"
Your product is a B2B performance-marketing middleware that connects the betting operators' backend systems directly to private dark social groups via a automated, compliant link-wrapping engine.
The Pure Solution
You build a zero-install web application for everyday sports fans (the "Micro-Tipsters").
	1. The tipster inputs a standard booking code from a bookmaker into your portal.
	2. Your system wraps that code into a dynamic, trackable Social Slip Link (e.g., slip.ke/xyz7).
	3. Your engine automatically injects the legally required GRA/BCLB compliance headers, 20% responsible gaming text, and over-18 warnings directly onto the destination landing page.
	4. When regular users click that link in WhatsApp, the exact bet slip populates in their local betting app via deep-linking.
3. The Business Model & Revenue Avenues
Because you are the technical layer enabling the transaction, you don't take on any gambling risk. You operate as an ad-tech utility.
Revenue Stream	How It Works	Target Metric
CPA Bounties (Primary)	Betting operators pay you a Cost-Per-Acquisition fee for every new depositing player or a Cost-Per-Bet fee on active wagers driven through your links.	You split this 70/30 with the micro-tipster to incentivize them to keep sharing.
B2B SaaS License	Tier-1 betting operators pay a monthly subscription fee to access your compliance dashboard, giving them real-time visibility into which dark social clusters are driving the most traffic.	Fixed monthly enterprise retainer per betting brand.
M-Pesa Micro-Payout Fees	When tipsters withdraw their earnings, your platform handles the bulk B2C M-Pesa payout. You charge a tiny fractional convenience fee per transfer.	Transactional micro-fees.
4. Value Proposition to Stakeholders
To the Betting Operator (The Buyer)
	• 100% Risk-Mitigated Traffic: The operator doesn't hire influencers. The traffic is driven by everyday peers sharing text links. The software handles all mandatory regulatory stamps automatically.
	• Attribution in Dark Social: They finally get data on which private WhatsApp or Telegram communities are actually generating high-value wagers.
To the Micro-Tipster (The Supply)
	• Instant Monetization: The regular "football genius" in a neighborhood group can finally get paid automatically via mobile money for their winning predictions, turning their hobby into a structured micro-income stream.
To the Regulator (The Shield)
	• Embedded Compliance: Your platform ensures every single peer-to-peer shared link enforces responsible gaming reminders and blocks underage access via mandatory redirect screens, actively helping the GRA clean up the market.

Project structure prod ready

Let’s officially graduate RadaSlips to a production-grade engineering enterprise. The name is exceptional—it carries immediate credibility in the local East African market ("rada" signaling sharp awareness, alerts, and insider insight) while clearly communicating its core utility for sharing and converting slips.
To build this "all the way" without hitting architectural bottlenecks later, we will drop any notion of a temporary prototype. We are setting up a decoupled, domain-driven workspace backed by PostgreSQL and Redis.
Because your background is in Django and React, we will use NestJS for the API (which is conceptually the TypeScript spiritual successor to Django) and Next.js App Router for the frontend deck. Here is your ultimate production blueprint. 
1. The Backend Engine (radaslips-api)
In NestJS, code is organized into Modules. Think of these as your isolated Django Apps. Everything related to a specific domain lives in one place, making the codebase completely modular and easy to maintain.

│   └── schema.prisma         # Single source of truth for PostgreSQL database tables

│   │   ├── guards/           # JWT Authentication guards
│   │   ├── prisma.service.ts # Database connection instance

The Django-to-NestJS Mental Translation
To help you move fast, map your existing Python architecture habits to this new TypeScript stack:
NestJS (TypeScript)	Django / DRF Equivalent	Production Purpose
Module (.module.ts)	Django App	Isolates domain logic physically and logically.
Controller (.controller.ts)	urls.py + Class-Based Views	Handles HTTP request methods, URL routes, and status codes.
Service (.service.ts)	services.py / Fat Models	Executes heavy business logic, database mutations, and external APIs.
DTO (.dto.ts)	DRF Serializer	Strict payload validation (ensures incoming JSON is properly shaped).

The Secret Weapon: app/r/[code]/route.ts
Notice that the WhatsApp link wrapper (/r/[code]) is not a visual React page (page.tsx). It is a pure Server Route Handler (route.ts). When a user taps a link on WhatsApp, this endpoint catches the request, logs the click metadata to Redis/PostgreSQL in the background, and instantly fires an HTTP 302 Found redirect to the destination bookmaker—keeping your visual rendering layer completely unburdened.
3. The Rollout Sequence
To bring this stack to life locally without tripping over cross-Origin Resource Sharing (CORS) or missing database dependencies, execute your rollout strictly in this order:
1.Provision the PostgreSQL Database & Schema:Prerequisite — Do this before writing any backend logic.
Initialize your base radaslips-api repository, set up your connection string in .env, and write your initial data models (Users, Slips, ClickLogs) inside schema.prisma. Run npx prisma db push to generate your database tables.
2.Scaffold the NestJS API Domain Modules:Port 3000 — Handles core business validation.
Use the Nest CLI (nest g resource slips) to generate your core controllers and services. Wire up your PrismaService so your backend can read and write betting codes to the database.
3.Build the High-Speed Link Redirector:Critical performance path — Keep execution under 50ms.
Inside your Next.js app, write the route handler at src/app/r/[code]/route.ts. Configure it to read the slug, ping the backend API to register a click, and execute a native NextResponse.redirect() to the final betting URL.
4.Construct the User Facing Dashboard:Port 3001 — Consumes API via React Server Components.
Build your interactive UI components (input fields for pasting original booking codes, conversion configuration panels, and shareable link generators) inside src/app/dashboard/slips/page.tsx.
